## Known limitations (read before trusting the numbers above)

1. **This is not a held out test.** Prompts and engine rules were debugged against these same 15 documents. A perfect line score here says the pipeline handles these planted edges; it does not predict accuracy on an evaluator's own file. No truth values or planted phrases were copied into prompts (checked by grep), but every fix was prompted by a failure seen on this set.
2. **One run is one sample.** Model output varies between runs. In one V5 run the blanket "same as last year" statement came back at match confidence 0.80 (below the 0.85 bar) and in others at 0.85 or more. Code now verifies that kind of scope deterministically (DECISIONS D21), but other borderline confidences can still flip a cell between Confirmed and Needs review from run to run. That flip only ever moves toward more review, never toward a silent wrong value.
3. **Questionnaire labels we disagree with (3 of 60).** V4 Q1 and V5 Q1 answer "certificate attached" without stating a number or expiry, which the model marks partial and the answer key marks answered. The knockout still resolves correctly from the attached certificate's expiry. V5 Q2 ("testing outsourced to a lab") is marked answered "no" but inferred, so the knockout stays Pending with the tentative fail shown. The key marks it partial.
4. **Photo lines are never Confirmed.** All 30 V4 values were read exactly, but they stay Assumed by design (DECISIONS D2). A buyer must eyeball the crop.
5. **Certificates are read for facts only.** Name and expiry checks are deterministic, but a forged or edited certificate would not be detected.
6. **Email bodies are documents.** Cover notes cost a classification call each (about Rs 0.06) and are then skipped.

7. **Two further files are no longer held out.** A Metro Kraft spreadsheet and a Trident email were read once through Try your file, exposed four rule gaps (a doubled pack divisor, unmapped unit phrases, conditional prices shown as Confirmed, dropped vendor notes) and were used to fix them. Their raw replies are in `eval/fixtures` and are replayed by tests. They are regression tests now, not evidence of accuracy on unseen files (DECISIONS D100 to D108).

8. **Three files are no longer held out.** A WhatsApp chat from a packaging vendor was read once through Try your file and exposed a tax basis gap (an inclusive price shown as an excluding GST price), a box size mismatch and a stored label that counted sandbox runs. They were fixed against that file's reply, which is in `eval/fixtures` and replayed by tests. It is a regression test now, not evidence of accuracy on unseen files (DECISIONS D109 to D115).
9. **Tax statements are read by regular expressions, and checked.** `engine/tax.ts` reads the vendor's own words ("GST included (12%)", "+ GST", "excl. GST") on a line, in the notes and in the document text. The Try your file prompt (`extract.v4`) also asks the model for a per line tax basis, rate and source quote, which code uses only when the quote is verbatim in the document, covers the line and contradicts nothing (DECISIONS D118). A vendor who words a statement in a way the expressions cannot read (another language, no tax word) is seen only if the model reports it and its quote is in the text. A line that only says "GST extra" under an unknown document basis stays Assumed.
10. **Box sizes depend on the model's description.** The size check parses the vendor's description or evidence quote. Inch sizes work only when the text says inch (or a quote mark), or the numbers are 100 or more (read as mm); a bare "14x10x8" is not guessed. The check flags a wrong match only when another RFx line of the same ply fits; it never re-maps. It runs at extraction, so lines stored before it carry no size note, and the 6 percent tolerance is a rule of thumb. Two pallet or tray sizes with no ply are compared for a note but never flagged.
11. **Validity units.** A validity in another language is read when its time unit is on the short list in `engine/terms.ts`. A date ("valid till 31 Dec") or an unlisted word gives no days and no warning.
12. **New findings are not in the stored review queue.** `tax_conflict` and the size and duplicate findings produce review items on Try your file only. The stored pipeline carries the flags on the lines (and the Assumptions panel lists `tax_basis_conflict`), but does not add separate open items for them.
13. **A replay on one captured sample did not predict the live result.** The tax rule passed a replay of a captured Gupta reply (D110) and failed on the next production upload, because the model put the correction in the notes instead of on each line. The first version of the guard (D117) passed every replay and the live reply got past it, because the model set the document basis to excl and put nothing about GST in the notes. The fix was checked by replaying that live reply against the real file text and by removing every tax answer the model gave, not by a second live run. Model output varies between runs, so a different shape may still appear. The guard is built to fail toward Not derived, not toward a price.
14. **Not derived is conservative, and the app cannot clear it.** A line with no tax statement of its own is Not derived whenever the document's statements conflict, or a statement that covers the line says the other way from the basis it would get. Metro Kraft's cartons used to be in this group (their note says rates incl. GST are shown for cartons while the basic rate is the quoted price); since D123 that note is informational and they derive. A buyer check or an edited value does not turn such a line into a price; the vendor has to settle it, or the source be corrected.
15. **The tax checks work from document text.** For a PDF read natively or a photo there is no text, so statements are taken from the notes and from the model only, and a model quote cannot be verified (H2 never resolves, H1 applies). The stored pipeline stays on `extract.v3` (so its cached replies stay valid) and gets H1 but not H2; a stored line extracted before this change carries no document statements, which is why the stored comparison could not move.
16. **Two production reruns showed regressions that replay did not predict (D122).** Metro Kraft came back with all 24 lines Not derived, because the sheet's column header row and a "for your convenience" note were read as tax statements; the Gupta tape lost its pack size because the extract.v4 reply carried no unit definition; and a "5ply boxes are BF 22 only" note flagged 3 ply lines. The replays missed the first because the vendor file text is not stored in a fixture, so no header row was ever replayed. Both files were then run live once each and gave the expected result (D127), but a third shape can still appear. The Gupta live rerun did not repeat the BF note, so the 3 ply grade fix is covered by tests only.
17. **Header and informational detection are heuristics.** A header is a row of short non numeric cells above a row with a number, or a plain text line of column words above a line of numbers; a header the heuristic does not recognise is still read as text. "For convenience", "for reference", "for information" and the basic rate wording make an inclusive figure informational; other wording ("indicative", a note in another language) does not, and an informational note worded that way would still send the covered lines to Not derived. That is the safe direction.
18. **The column a price was read from is not checked.** On a dual column sheet the quote is the basic column, but code does not verify that the model read the number from it. If the model picked the incl tax cell, the price is treated at the document basis and is too high by the tax. The evidence drawer shows the cell, so a buyer can see it. Superseded by D128 (K5b): the row's other cells are now compared with the model's price.

19. **Header detection is for spreadsheets only, and it is a heuristic (D128).** A price cell is mapped to the nearest text cells above it in its column. A Word table, a PDF or a photo has no such grid in the prepared text, so those inputs keep the document level logic of D117 to D123 and still depend on what the document says. A text cell in the price column of a data row (for example "On request") is read as the header and states nothing, which leaves that line to the existing logic. A header whose wording is outside the word list (another language, "Rate + tax extra") states nothing. A sheet whose header says excluding tax and whose own terms row says including tax is Not derived for the lines the terms row covers: the safety rule trades a wrong number for a false alarm, on purpose. K5b compares the model's price with the other cells of the row, so a "Total amount incl GST" column next to a unit rate column can be mistaken for the including-tax rate; it only matters when the model's price equals that total.

## Lessons from live reruns

(a) A fix that passed a replay of one captured sample failed on the next live run, because the model varies: the same file came back with a differently worded tax note, and the guard that quoted it flipped 12 lines to Not derived. (b) A table header row was read as a tax statement because no replay fixture held the vendor file text, so the replay never saw the header the live run quoted. (c) A guard that read the model's own notes depended on the model's wording, so the final design (K5) reads the sheet itself and ignores the notes for any line with a header basis. (d) A strict safety rule trades wrong numbers for false alarms: Not derived is the right answer when a header and a terms row disagree, and it will sometimes fire on a harmless sheet.
